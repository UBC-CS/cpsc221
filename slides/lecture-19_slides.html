Monday’s tree (no 40). Quick replay, asking the room what will happen before each click:

  1. Delete 37, a leaf: it just disappears. Its parent’s pointer becomes null.
  2. Delete 51, one child: 84 moves up into its place. Everything under 84 is still bigger than 38, so the tree is still a BST.

The point to land: in both cases, one pointer in the tree changes — the one that used to point at the doomed node. That’s the hook for the code.

Binary search tree — remove

Remember: find_ returns the pointer in the tree, by reference.

Node *& find_(const K & key, Node *& r) {
    if (r == nullptr) return r;
    else if (r->key == key) return r;
    else if (key < r->key) return find_(key, r->left);
    else return find_(key, r->right);
}

Node *& p = find_(key, root);
if (p != nullptr)                                  // found it (else: nothing to do)

The whole idea: find it, then fix up the pointer you found. Because find_ returns Node *&, p is the parent’s left or right (or root itself), not a copy. Assigning to p rewires the tree.

Same trick as insert on Monday: Node *& p = find_(key, root); if (p == nullptr) p = new Node(key, data);. Insert fixes up a null pointer; remove fixes up a non-null one.

BST — remove

void zeroOneChildRemove(Node *& p) {
    Node * temp = p;
    if (p->left == nullptr) p = p->right;
    else                    p = p->left;
    delete temp;
}

remove(37):   p is 25’s right

remove(89):   p is 84’s right

p is a reference to the parent’s pointer, so reassigning it splices the node out:

  • 37 is a leaf: p->left is null, so p = p->right, which is also null. 25’s right pointer becomes null. The leaf case comes for free.
  • 89 has one child: its left is null, so p = p->right, and 84’s right pointer now points at 95.

temp keeps the old address so we can free the node after rewiring. Ask: what goes wrong if we delete p first? (Then p->right reads freed memory.)

Both the zero- and one-child cases in four lines, and Θ(h): the cost is the find_.

2-child remove

T.remove(38); How should we implement this?

How can you rearrange what’s left into a BST?   Describe as many ways as you can.

About 3 minutes in pairs, then collect answers on the board. Expect:

  1. Hang TR under the largest key in TL: 13 becomes the root, and 51’s whole subtree goes on 37’s right. Legal — every key in TR is bigger than everything in TL. Height: 6.
  2. Hang TL under the smallest key in TR: 51 becomes the root, 13’s subtree goes on 40’s left. Legal. Height 4 here, but only by luck: in general the heights add.
  3. Promote 37, the largest key on the left (in-order predecessor), into the hole. Height 4.
  4. Promote 40, the smallest key on the right (in-order successor). Height 4.

All four are correct BSTs. Which do we want? Everything costs Θ(h), and 1 and 2 can make the tree taller (heights add); 3 and 4 never do, since only one node moves. Wrong-but-common guesses: “13 or 51 moves up” with nothing else changed — 13 at the root would leave 25 and 37 on its left, 51 would leave 40 on its right.

We’ll use the predecessor. Where is it? Go left once, then right as far as you can. Note that 37 and 40 sit on either side of 38 in the inorder traversal: …, 25, 37, 38, 40, 51, …

Watch:

Step mode is already on, and the tree has 40 in it. Delete 38, and press Step at each move: the search finds 38, then walks left once, right to the end to 37, copies 37 up into the root, and removes the old 37 node, a leaf, the easy case.

Ask before each step: where does it go next?

Then keep removing the root: delete 37 (predecessor 25), then 25. That third one is the tricky case: go left to 13, and 13 has no right child, so 13 is the rightmost node of the left subtree. The root becomes 13, and 13’s old node is spliced out: 10 moves up. In the code (next slide), rightMost_(p->left) returns p->left itself, and zeroOneChildRemove rewires it. No special case.

Binary search tree — remove

void twoChildRemove(Node *& p) {
    Node *& iop = rightMost_(p->left);
    p->key  = iop->key;
    p->data = iop->data;
    zeroOneChildRemove(iop);
}
Node *& rightMost_(Node *& r) {
    if (r->right == nullptr) return r;
    else return rightMost_(r->right);
}

iop = in-order predecessor. rightMost_ is a find, too: it returns the pointer in the tree that points at the rightmost node: 25’s right, here.

Copy the predecessor’s key and data up into p’s node, then remove the predecessor’s node. It’s a rightmost node, so it has no right child: it’s always the easy case. One call, never a chain.

Running time: down to 38, then down to its predecessor: one path, still Θ(h).

How many “bad” \(n\)-item trees are there?

Binary Search Tree … running time Θ(h).

Inserting keys in sorted order — 2, 7, 15, 22, 28 — builds a stick: every key goes right. (Monday’s list B.) Live: in the explorer, Clear and insert them, and watch the height readout climb with n. Height \(n - 1\), so every operation is \(\Theta(n)\). Our “fast” dictionary is a linked list.

“Bad” trees: any shape where every node has at most one child, like the zig-zag. Each of the \(n - 1\) links below the root goes left or right: \(2^{n-1}\) of them.

Binary search tree — height

Reminder: height(T) is

  • ______ if T is empty
  • 1 + max(height(TL), height(TR)), otherwise

The algorithms on BST depend on the height (\(h\)) of the tree.

The analysis should be in terms of the amount of data (\(n\)) the tree contains.

So we need relationships between \(h\) and \(n\):

\(h \ge f(n)\)

\(h \le g(n)\)

Empty tree: height −1.

We know find/insert/remove cost \(\Theta(h)\). To say anything in terms of \(n\), we need to pin \(h\) between two functions of \(n\) — that’s the next slide.

Thus: lower bound on height ______, upper bound on height ______ — good news or bad (what’s the context?)

#1: at most \(2^{h+1} - 1\) nodes (perfect tree), so \(n \le 2^{h+1} - 1\) and \(h \ge \log_2(n+1) - 1\): \(h = \Omega(\log n)\).

#2: a stick has height \(n - 1\): \(h = O(n)\).

Lower bound \(\Omega(\log n)\), upper bound \(O(n)\). For a dictionary that’s bad news: the worst case is a linked list.

All 5040

Press Build the trees at n = 7: every insertion order, exactly.

80 perfect, 64 sticks: both rare. Most land in the middle, height 3 or 4. Average 3.67.

Then n = 100, 1,000, 10,000 (1,000 random orders each). The tallest possible height runs off the chart (99, 999, 9,999), but the trees pile up at a few times log n: around 12 for n = 100, 21 for 1,000, 30 for 10,000. Random BSTs are short. On average the height is Θ(log n).

The catch: the stick isn’t rare in real life. Sorted input, the most common input there is, builds it every time.

Average case!

The height of a BST depends on the order in which the data is inserted into it.

    ex.  1 3 2 4 5 7 6   vs.   4 2 3 6 7 1 5

How many different ways are there to insert \(n\) keys into a tree?

Avg height, over all arrangements of \(n\) keys, is ________.

operation avg case worst case sorted array sorted list
find \(\log n\) \(\log n\)
insert \(n\) \(n\)

1 3 2 4 5 7 6 builds a tall, stringy tree (height 4); 4 2 3 6 7 1 5 builds a bushy one (height 2). Same keys, different order.

There are \(n!\) insertion orders. Averaged over all of them, the height is \(\Theta(\log n)\) (a classic result we won’t prove).

avg worst sorted array sorted list
find log n n log n n
insert log n n n n
delete log n n n n
traverse n n n n

Planted error: sorted list find is shown as \(\log n\). It’s \(n\): no binary search without random access, so you walk the list. (Sorted array find really is \(\log n\).) Ask: “one of these is wrong — which?”

So BSTs are great on average — but the worst case is exactly what sorted input produces. Can we make the worst case \(\log n\) too?
