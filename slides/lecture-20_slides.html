How many “bad” \(n\)-item trees are there?

Binary Search Tree … running time Θ(h).

Inserting keys in sorted order — 2, 7, 15, 22, 28 — builds a stick: every key goes right. (Monday’s list B.) Height \(n - 1\), so every operation is \(\Theta(n)\). Our “fast” dictionary is a linked list.

“Bad” trees: any shape where every node has at most one child, like the zig-zag. Each of the \(n - 1\) links below the root goes left or right: \(2^{n-1}\) of them.

Binary search tree — height

Reminder: height(T) is

  • 1 + max(height(TL), height(TR)), otherwise

The algorithms on BST depend on the height (\(h\)) of the tree.

The analysis should be in terms of the amount of data (\(n\)).

So we need relationships between \(h\) and \(n\):

\(h \ge f(n)\)

\(h \le g(n)\)

Empty tree: height −1.

We know find/insert/remove cost \(\Theta(h)\). To say anything in terms of \(n\), we need to pin \(h\) between two functions of \(n\) — that’s the next slide.

Thus: lower bound on height ______, upper bound on height ______ — good news or bad?

#1: at most \(2^{h+1} - 1\) nodes (perfect tree), so \(n \le 2^{h+1} - 1\) and \(h \ge \log_2(n+1) - 1\): \(h = \Omega(\log n)\).

#2: a stick has height \(n - 1\): \(h = O(n)\).

Good news or bad depends on the context. Lower bound \(\Omega(\log n)\), upper bound \(O(n)\). For a dictionary that’s bad news: the worst case is a linked list.

A tree is height balanced if - it’s empty, or - \(|b| \le 1\) at the root, and both subtrees are height balanced.

The recursion matters: the root being balanced isn’t enough. A BST that is height balanced everywhere is what the rest of today is about: how to keep it that way as keys come and go. (It gets a name once we’ve built it.)

Left rotation

A left rotation about 80: 80’s right child, 90, takes its place.

  • 80 becomes 90’s left child.
  • 90’s old left child, 85, becomes 80’s right child. It has to go somewhere, and it fits: 80 < 85 < 90.
  • 60, and 99 with 95, move along untouched.

In-order before and after: 60 80 85 90 95 99. Same order, so still a BST.

The subtree rooted here had height 2 before the insert, 3 after it, and 2 again after the rotation. So nothing above it changes: 50 goes from +2 back to +1. One rotation fixed the whole tree.

Left rotation, in general

Before

After

void rotateLeft(Node *& t) {
    Node * s = t->right;
    t->right = _______;
    s->left  = _______;
    t        = _______;
    updateHeight(t->left);
    updateHeight(t);
}
int height(Node * t) {
    return t == nullptr ? -1 : t->height;
}
void updateHeight(Node * t) {
    t->height = 1 + max(height(t->left), height(t->right));
}
t->right = s->left;     // T2 moves across
s->left  = t;           // 10 goes under 20
t = s;                  // the pointer IN THE TREE now points at 20

t and s are pointers, not nodes. t is the parent’s child pointer (or root), passed by reference: the same Node *& trick as remove. So t = s hangs the rotated subtree back in the tree.

It’s swap, generalized. Swap is tmp = a; a = b; b = tmp;: grab one value, then each line’s right side is the previous line’s left side. Here: s = t->right; t->right = s->left; s->left = t; t = s;, the same chain. Three pointer slots (the tree pointer, 10’s right, 20’s left) hold (10, 20, T2) before and (20, T2, 10) after: a 3-way rotation of values. Swap is the 2-way version.

  • In-order T1 10 T2 20 T3 is the same before and after: still a BST.
  • Local: T1, T2, T3 move as whole subtrees; nothing inside them changes.
  • Constant time: three pointer assignments, two height updates.
  • Whose heights change? Only 10 and 20. After t = s, t points at 20 and t->left at 10. Update 10 first (t->left): it’s now 20’s child, and 20’s height depends on it.

The nodes now store their height (int height in Node), so height() is O(1), not a traversal.

A right rotation is the mirror image: swap every left and right.

Balanced trees: summary

Rotations:

  • four kinds: left, right, left-right, right-left (mirror images)
  • local: whole subtrees move; nothing inside them changes
  • constant time: a few pointer changes and height updates
  • the BST property is kept: the in-order traversal doesn’t change


GOAL: use rotations to keep a BST height balanced, on every insert and remove.


Height-balanced BSTs, kept that way by rotations, have a special name:   AVL trees


Still to work out:   Which rotation?   Where in the code?

Named for Adelson-Velsky and Landis (1962).

Each rotation is O(1) no matter how big the tree is: we never look inside the subtrees that move. Insert needs at most one rotation (single or double); remove can need one per level, \(O(h)\).

There are other balanced-tree schemes (red-black trees, for one): Monday’s intro.

Which rotation?

An insert into t’s right subtree made \(b = +2\) at t.

If it went into T4 or T5, a __________ rotation about t fixes it.

    We can tell: balance at t->right is ____

If it went into T2 or T3, a __________ rotation about t fixes it.

    We can tell: balance at t->right is ____

  • T4 or T5, outside: a stick t → r → y. Single left rotation. Balance at t->right is +1 (r leans right).
  • T2 or T3, inside: a bent stick t → r → x. Right-left double rotation. Balance at t->right is −1 (r leans left).

So we don’t need to remember where the key went: the child’s balance tells us. Mirror image for \(b = -2\): child −1 → right, child +1 → left-right.

(After an insert the child is never 0. After a remove it can be, and then a single rotation is the right one. The code on the next slide handles it.)

AVL insert

void insert(Node *& t, const K & key) {
    if (t == nullptr)
        t = new Node(key);
    else if (key < t->key)
        insert(t->left, key);
    else if (key > t->key)
        insert(t->right, key);
    rebalance(t);
}

Lecture 18’s insert, plus one line.

void rebalance(Node *& t) {
    int b = balance(t);
    if (b == 2) {
        if (balance(t->right) >= 0)
            rotate__________(t);
        else
            rotate__________(t);
    }
    else if (b == -2) {
        if (balance(t->left) <= 0)
            rotate__________(t);
        else
            rotate__________(t);
    }
    else updateHeight(t);
}
b ==  2:  child >= 0 → rotateLeft        else → rotateRightLeft
b == -2:  child <= 0 → rotateRight       else → rotateLeftRight

with int balance(Node * t) { return height(t->right) - height(t->left); }.

Where’s the “check every node on the path”? It’s the recursion: rebalance runs as each call returns, so it visits 95’s parent, then grandparent, and so on up to the root, bottom up. The first unbalanced node it meets is the lowest one, just like we did by hand.

Every node on the path gets its height updated: by updateHeight, or by the rotation.

>= 0, not == 1: after an insert it’s always ±1, but rebalance is also what remove will use, and there the child can be 0.

Running time: the path is \(O(h)\), and each step is \(O(1)\).

AVL remove

Remove as in a BST, then rebalance every node on the path back up to the root.

T.remove(9);   What happens?

Pause the video and try it.

  1. 9 is a leaf: it’s just removed. Now 10 has \(b = +2\) (left −1, right 12 has height 1). 10’s right child, 12, is −1: a bent stick, so a right-left rotation about 10. 11 comes up: 11(10, 12).
  2. That subtree’s height dropped from 2 to 1, so its parent changes too: 8 now has \(b = -2\) (left height 3, right height 1). 8’s left child, 5, is −1: a right rotation about 8. 5 becomes the root.

Result: 5(3(1(·, 2), 4), 8(6(·, 7), 11(10, 12))).

Two rotations. An insert rotation puts the subtree back at its old height, so it stops there. A remove rotation can leave the subtree shorter, and then the parent may need fixing too, all the way up: up to \(O(h)\) rotations.

The code: BST remove, written recursively, with rebalance(t) on the way back up, the same line we added to insert.
