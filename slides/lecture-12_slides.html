Queue — linked memory implementation:

template<class SIT>
class Queue {
public:
    // ctors dtor
    bool empty() const;
    void enqueue(const SIT & e);
    SIT dequeue();
private:
    struct queueNode {
        SIT data;
        queueNode * next;
    };
    queueNode * entry;
    queueNode * exit;
    int size;
};

What is the running time of enqueue?


What is the running time of dequeue?

exit points at the front (8), entry at the back (4).

  • enqueue adds after the back node and moves entry: \(\Theta(1)\).
  • dequeue removes the front node and moves exit: \(\Theta(1)\).

Ask what happens if they are the other way round. Adding at the front is fine, but removing from the back of a singly linked list means walking to the node before it: \(\Theta(n)\). So the direction of the arrows decides which end is which.

Trace it with two indices, front and back, instead of shifting anything.

After the first column the queue is just 7, sitting at index 3. After enqueue 2, 1, 3, 5 it fills indices 3–7: the end of the array. One more dequeue leaves 2 1 3 5 in indices 4–7.

Now enqueue(9): there’s no room at the end, but indices 0–3 are empty. Shifting everything left would cost \(\Theta(n)\) per dequeue. The better idea: wrap around and put 9 at index 0. That’s the next slide.

The blank lines in private: are for the class to fill in: int exit; and int size;. The back of the queue isn’t stored — it’s (exit + size) % capacity.

Trace: m o n d a y fill 4–7 and wrap to 0–1; i s fill 2–3. The array is full: m o n d a y i s. dequeue returns m and moves exit to 5. enqueue(h) goes in the slot m left, index 4. Now enqueue(a) finds it full again, so resize: copy into the long array in queue order, starting at exit — o n d a y i s h — and then add a. Exit becomes 0.

Same doubling as Friday’s video, so both operations are \(\Theta(1)\) on average.

Why consider an array?

Blanks: constant, constant, \(O(n)\), \(O(1)\). That last pair is Nathan’s resizing video in one line: doubling makes the total cost of \(n\) pushes linear, so each push is constant on average.

Why an array at all: no pointer stored with every item, so less memory; the items sit next to each other, so the cache helps; and you can index into the middle in constant time. The queue gets all the same answers.

Running time?

The blank: an array whose two halves are each sorted.

Walk two fingers, one at the start of each half. Copy the smaller of the two into the output and advance that finger. When one half runs out, copy the rest of the other.

Every element is copied exactly once, so this is merge, and it is \(\Theta(n)\).

OK, then sort this array:

Split it in half. If each half were sorted, one merge would finish the job in linear time.

So how did the halves get sorted? Leave them hanging: that’s merge sort, in Friday’s video.

mergeSort

  1. If the array has 0 or 1 elements, it’s sorted.
  2. Split the array into halves.
  3. Sort each half recursively.
  4. Merge the two halves.
void mergeSort(vector<T> & A, int lo, int hi) {
    if (hi > lo) {
        int mid = (hi + lo)/2;
        mergeSort(A, lo, mid);
        mergeSort(A, mid+1, hi);
        merge(A, lo, mid, hi);
    }
}
