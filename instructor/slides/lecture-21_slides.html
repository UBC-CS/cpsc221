How big can \(h\) be, for an AVL tree with \(n\) nodes?

All three operations walk one path, so all three are \(O(h)\) for both trees. For a plain BST, \(h\) can be \(n - 1\). Today’s question is what \(h\) can be for an AVL tree. Answer, by the end: \(O(\log n)\).

AVL tree analysis

We want: \(h = O(\_\_\_\_\_\_\_\_)\).


An upper bound on the height of a tree with \(n\) nodes

is the same as

a lower bound on the number of nodes in a tree of height \(h\).


Define \(N(h)\): the least number of nodes in an AVL tree of height \(h\).

\(h = O(\log n)\).

Why the switch: if every AVL tree of height \(h\) has at least \(N(h)\) nodes, then a tree with \(n\) nodes has \(n \ge N(h)\), and turning that around bounds \(h\). Counting nodes in the skinniest possible tree is easier than reasoning about the tallest possible tree directly.

For all \(h \ge 0\).

  • Case 1, \(h = 0\): the tree is one node, and \(1 \ge 2^0 = 1\).
  • Case 2, \(h = 1\): the tree has at least 2 nodes, and \(2 \ge 2^{1/2} \approx 1.41\).
  • Case 3, \(h \ge 2\): one subtree of the root has height \(h-1\), and the other has height at least \(h-2\) (the balance condition). Both are AVL trees, so by an inductive hypothesis that says every AVL tree of height \(j < h\) has at least \(2^{j/2}\) nodes, the subtrees have at least \(2^{(h-1)/2}\) and \(2^{(h-2)/2}\) nodes. Since \(2^{(h-1)/2} \ge 2^{(h-2)/2}\), the tree has at least \(1 + 2 \cdot 2^{(h-2)/2} > 2^{h/2}\) nodes.

Two base cases because case 3 reaches back two heights.

Classic balanced BSTs

AVL trees: height at most \(1.44 \log_2 n\)

______ rotations on find

Red-black trees: height at most \(2 \log_2 n\)

A constant number of rotations on insert and on remove


And others: 2-3 trees, splay trees, treaps, …

AVL: 0 rotations on find; at most 1 (single or double) on insert, since the rotation puts the subtree back at its old height; up to \(O(\log n)\) on remove, since a rotation can leave the subtree shorter (lecture 20’s example).

Red-black trees allow more imbalance (height up to \(2 \log_2 n\)) in exchange for fewer rotations: at most 2 on insert, at most 3 on remove. They are what std::map uses. We won’t cover them; this is the “there are others” mention.

Balanced BSTs, pros and cons

Pros

  • insert, remove, and find are always \(O(\log n)\)
  • An improvement over ______________
  • Range finding and nearest neighbour


Cons

  • It is possible to search for single keys faster
  • If the data is too big for memory, it lives on disk, and we need a different structure

An improvement over plain BSTs (worst case \(O(n)\)) and over sorted arrays or linked lists for a changing set of keys.

Range finding: all keys between \(a\) and \(b\), in order. Nearest neighbour: the closest key to a value. A tree does both naturally; a hash table, which is coming, cannot.

The two cons are the two roads out of here: faster single-key search is hashing (next time), and data on disk is B-trees (now).

Out of core: the data lives in external storage (disk, SSD, or a server across a network), and only some of it is in memory at any time.

Big-O counts operations as if each costs one unit. Fetching from disk breaks that assumption badly, as the next slide shows.

The story on disks

How many disk seeks to find a record?

  • 2 million instructions per millisecond.
  • A hard-disk seek is about 5 ms, so about 10 million instructions’ worth of waiting. (An SSD read is closer to 0.1 ms: faster, but still about 1000 times slower than memory.)
  • Records: about 300 million licensed drivers. At 1 KB each, about 300 GB: more than a laptop’s memory.
  • Depth: between \(\log_2 (3 \times 10^8) \approx 28\) and \(1.44 \times 28 \approx 41\) levels.
  • Seeks: one per level if every node is a separate read, so up to about 41 seeks, about 0.2 seconds for one lookup. The instructions to compare keys are free by comparison.

The story on disks, continued

Suppose we weren’t careful…


Following one pointer costs one disk read.


So the number of disk reads is

____________.

Every node of the tree is somewhere else on the disk, so each step down the tree is another read. The number of reads is the height of the tree. To make lookups fast, make the tree as shallow as possible. Comparisons inside a node are cheap; it’s moving between nodes that costs.

B-tree of order \(m\)

Goal: minimize the number of reads from disk.

  • Build a tree that uses one disk block per node
    • A disk block is the fundamental unit of transfer
  • Nodes have more than one key
  • The tree should be balanced and shallow
    • In practice, branching factors over 1000 are common

If one read brings in a whole block anyway, fill the block: a node holds as many keys as fit. More keys per node means more children per node, which means a shallower tree, which means fewer reads.

B-tree of order \(m\): a node

Every node has room for \(m - 1\) keys, but __________________.

If a node has \(i\) keys, then it has ________ child pointers.

The keys in a node are in order.

  • …but it isn’t always full: a node may have fewer keys (down to a minimum, on the next slide).
  • \(i\) keys, \(i + 1\) child pointers (for an internal node). Child \(j\) holds the keys between key \(j\) and key \(j + 1\): the BST rule, generalized.

The key slots are an array, so a node can be searched by binary search.

Definition of a B-tree

A B-tree of order \(m\) is an \(m\)-way search tree in which:

  • Every node holds at most \(m - 1\) keys, in order
  • An internal node with \(i\) keys has \(i + 1\) children
  • Every non-root node holds at least \(\lceil m/2 \rceil - 1\) keys
  • The root holds at least 1 key
  • All leaves are on the same level

Ask: what is the order of this tree?

  • At most 4 keys in a node (52 53 55 68), so \(m - 1 \ge 4\): \(m \ge 5\).
  • Non-root nodes with only 2 keys, so \(\lceil m/2 \rceil - 1 \le 2\): \(m \le 6\).
  • So 5 or 6. Both satisfy the definition. But if it were order 6, the root could have held 3 8 17 28 48 in one node; it only splits into 2 + 1 + 2 at order 5 (insertion isn’t covered this term, so this part is a teaser).

Check it against the rules with them: each internal node has one more child than keys; every leaf is at depth 2; the keys between 8 and 17 (12, 14, 16) are in the child between 8 and 17.

The minimum keeps the tree from going thin, which is what keeps it shallow: every non-root node has at least \(\lceil m/2 \rceil\) children, so the height is \(O(\log_m n)\). Because all leaves are on the same level, the tree is perfectly balanced by definition, no rotations involved.

Back to the driving records

How many keys can a B-tree of order \(m\) and height \(h\) hold?


With \(m = 1000\): how tall is the tree for 300 million records?


How many disk reads to find a record?

At most \(m - 1\) keys per node, and at most \(m^d\) nodes at depth \(d\), so at most \(m^{h+1} - 1\) keys in all.

With \(m = 1000\): height 2 holds up to \(10^9 - 1\) keys, plenty for \(3 \times 10^8\). So 3 reads, against about 41 for the AVL tree, and in practice the root stays in memory, so 2.
