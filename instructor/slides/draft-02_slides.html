Algorithm analysis

Analysis of an algorithm gives insight into

  • whether it is correct
  • how long it runs — time complexity
  • how much memory it uses — space complexity

All with the aim of making comparisons between different approaches to solving the same problem analytically, not experimentally.

Thirty seconds. This is a framing slide, not a content slide.

Where we stopped

If an algorithm is not correct, is its value 0?


No — and the exceptions are important and worth considering:

  • approximation — provably close, much faster
  • heuristics — usually good, no promise
  • randomized — correct with high probability
  • restricted inputs — correct on the data you actually have

Measuring the value of algorithms

Two algorithms solve the same problem. Which is better?

  • Use different metrics — time, space most common
  • Express running time as a (positive) function of input size:

\[T(n): \text{time to complete the operations on data of size } n\]

 

 

  • The form of that function depends on the structure of the algorithm

Which of these are you willing to wait for?

Anchor: the universe is about 4.4 x 10^17 seconds old.

  • 10^12 s (n^2 at n=10^12) — ~32,000 years. About 5x all of recorded history; back to the Chauvet cave paintings.
  • 10^18 s (2^n at n=100) — ~32 billion years. 2.3x the age of the universe.
  • 10^24 s (n^3 at n=10^12) — ~32 quadrillion years. 2.3 million x the age of the universe.
  • 10^289 s (2^n at n=1000) — 10^271 x the age of the universe. There are only ~10^80 atoms in the observable universe; this exceeds that by 10^209.

If you only use one line: 2^n at n=100 already outruns the universe. Not a million. A hundred.

Small end: 10^-9 s is one nanosecond, and light travels 30 cm in it – Grace Hopper handed out 11.8-inch wires so engineers would stop asking why satellite calls were slow. At 10^-11 s light travels 3 mm.

Two framings if there is time:

  • The n^3 row is the scary one. 2^n is easy to dismiss as pathological, but n^3 is an innocent triple loop – and at n=10,000 it is already 1 second while n is still at 10^-8.
  • Faster hardware does not save you. A machine 1000x faster turns 10^289 into 10^286. The exponential eats all of hardware progress and doesn’t notice. That is why this is a math course, not a benchmarking course.

Example 1, continued

Read your statement out loud, simultaneously on the count of 3.

don’t fix it as you read! You are going to want to. You will see the gap about half a second before you reach it, and your instinct will be to quietly patch it as you speak.

Resist that. You are reading it so that you can hear it.

Let the whole room read at once – it takes about thirty seconds and the wall of sound is worth having. Two hundred people saying different sentences about the same four lines of code makes the point before anyone discusses anything.

Reading simultaneously does three things a round-robin cannot: it removes all performance anxiety in week 1 among strangers, it guarantees every single student actually does it, and it means no confident voice anchors the group before the others have spoken.

The instruction not to self-repair is the important one. Say it twice. Students patching their own sentences mid-read is automatic and it is exactly what destroys the effect.

Example 1, continued

Share your statements, and discuss them.

Write a final description for your group.

Circulate. Listen for the argument – the groups doing this properly get loud. Silent groups usually accepted the first statement without testing it.

Useful nudge if a group is stuck agreeing: “read me the shortest one, and I’ll tell you how I’d break it.”

Example 1, continued

int ____________ (vector<int> arr, int q) {
    for (int i = 0; i < arr.size(); i++)
        if (arr[i] == q)
            return i;
    return -1;
}

Build it live from the room’s own words. Take pieces from different groups so the final sentence visibly belongs to everyone.

A version that survives all the attacks above:

Given a vector of integers arr and an integer q, return the index of the first element of arr equal to q, scanning from index 0 upward. If no element equals q, return -1.

Then the name falls out almost for free: indexOfFirst, firstIndexOf, findFirstIndex. Point out that “find” alone was never enough – a function called find could return a bool, a value, or an iterator.

If somebody has instead transcribed the code line by line (“it loops from 0 to size, and if arr[i] equals q it returns i”), that technically passes the reimplementation test, which makes it a great 90 seconds: it tells you what the code says, never what it is for, and it is no shorter than just reading the code. The giveaway is that a transcription cannot name the function.

What just happened?

Deliberately bare – this part is talked, not projected. Prompts, in the order they tend to work:

  • Twenty minutes ago almost nobody could write that sentence. Now almost all of you can.
  • And I never taught you anything about searching an array. Say it, then stop. Let them work out why. Nothing was transmitted from the front of the room – what changed is that they talked to each other.
  • You needed each other. Not a lecture, not a recording, not a smarter person – two people who would not accept a vague sentence.
  • The contract: when one of you says something fuzzy, any of the others gets to say “say that more precisely.” Not rude. The most useful thing you can say to someone trying to learn this. They will hear me say it all term.
  • A recording gives you information. The room gives you feedback.

Do not add an attendance pitch. They just lived the argument; saying it a second time cheapens it.

What does it depend on?

Blanks are for the pen. What the room should land on:

  • the size of the array
  • where q is – or whether it is there at all
  • the speed of the machine

The third one is the one to kill: we are not benchmarking, so machine speed has to go. That is what forces us to count operations instead of seconds – and the first two are what force us into cases.

Best, worst, average

int idxFirst (vector<int> arr, int q) {
    for (int i = 0; i < arr.size(); i++)
        if (arr[i] == q)
            return i;
    return -1;
}

For an array of size \(n\):

  • best case   $T(n) = $
  • worst case   $T(n) = $
  • average case   $T(n) = $

Best: 1 – q is at index 0. Worst: n – q is last, or absent. Average: about n/2, and it is worth asking average over what? – you have to assume a distribution before “average” means anything. That assumption is where most average-case analysis quietly goes wrong.

Which of the three do we usually report, and why? Worst case: it is a promise you can actually make.
